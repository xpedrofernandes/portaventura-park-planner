# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

This repository is an early-stage Python data project — only a `.gitignore`, `requirements.txt`, and one data-prep script are committed so far. There is no README, no `pyproject.toml`, and no tests. Treat this as a greenfield project: there is no established architecture to preserve, so when adding code, establish structure deliberately rather than searching for conventions that don't exist yet.

## Environment

- Python 3.12 virtual environment at `.venv/` (Windows, created with the standard `venv` module). Activate with `.venv\Scripts\activate` (PowerShell: `.venv\Scripts\Activate.ps1`).
- Dependencies are frozen in `requirements.txt` (install with `.venv\Scripts\pip.exe install -r requirements.txt`). Re-freeze with `.venv\Scripts\pip.exe freeze > requirements.txt` after adding packages so the environment stays reproducible.
- Key packages: `pandas`, `numpy`, `scipy`, `pyarrow`, `lightgbm` (data/ML), `matplotlib`, `streamlit`, `altair`, `pydeck`, `pillow` (viz/dashboard), `anthropic`, `python-dotenv` (AI integration/config), `openpyxl` (reading the `.xlsx` sources).
- `.env` holds an `ANTHROPIC_API_KEY` and is git-ignored — never commit it or print its contents.

## Data

Raw source data lives in `data/raw/` (git-ignored — not committed to the repo, so don't assume it's present in a fresh clone):

- `attendance.csv` — daily park attendance: `USAGE_DATE, FACILITY_NAME, attendance`
- `entity_schedule.csv` — opening schedules and closures for parks/attractions: `ENTITY_DESCRIPTION_SHORT, ENTITY_TYPE (PARK/ATTR), DEB_TIME, FIN_TIME, WORK_DATE, REF_CLOSING_DESCRIPTION`
- `link_attraction_park.csv` — semicolon-delimited mapping of `ATTRACTION;PARK`
- `waiting_times.csv` — per-attraction, per-time-slot wait times and throughput: `WORK_DATE, DEB_TIME/FIN_TIME, WAIT_TIME_MAX, NB_UNITS, GUEST_CARRIED, CAPACITY, ADJUST_CAPACITY, OPEN_TIME, UP_TIME, DOWNTIME, NB_MAX_UNIT`
- `weather_data.csv` — hourly weather observations (OpenWeather-style schema): `dt, dt_iso, temp, humidity, wind_speed, rain_*, snow_*, weather_main, weather_description, ...`
- `glossary.xlsx`, `parade_night_show.xlsx` — Excel workbooks (reading them requires `openpyxl`, which is not currently installed in `.venv`)

Note the inconsistent delimiters/date formats across files (`link_attraction_park.csv` uses `;`, others use `,`; timestamp formats vary between files) — normalize explicitly rather than assuming a single parsing path works for all of them. Two parks appear in the data: PortAventura World and Tivoli Gardens.

`waiting_times.csv` is ~365MB spanning 2018-01-01 to 2022-08-18 (~3.5M rows) — never load it whole. Read it with `usecols` and `chunksize`, filter per chunk, then concatenate.

A row is "closed" (ride not operating) when `OPEN_TIME == 0` and `CAPACITY == 0`; `WAIT_TIME_MAX` is ~0 in that state. `DOWNTIME > 0` is a narrower, separate signal (ride breakdown) and only applies to a small fraction of rows — don't conflate the two.

Derived/processed datasets go in `data/processed/` (git-ignored, like `data/raw/` — regenerate via the scripts below rather than expecting it to exist after a fresh clone).

`data/rides.json` (committed — small, hand-curatable) has one entry per PortAventura ride (`name`, `min_height_cm`, `tags`, `zone`). `tags` are drawn from `src/tags.ALLOWED_TAGS`; `zone` is one of 5 invented zones (Thrill Peak, Coaster Canyon, Lagoon Cove, Kids Kingdom, Mystic Quarter) grouping rides that would plausibly sit near each other. **All of this — heights, tags, and zone layout — is fabricated/plausible-guess data, not sourced from a real PortAventura map or ride specs**; treat it as placeholder content to replace if real ride data ever becomes available, not as ground truth.

`data/zones.json` (committed, same fabricated-but-internally-consistent status) is the walking-time graph between those 5 zones — `zones` (name list), `adjacent` (each zone's ring-neighbours), and `walk_minutes` (full symmetric pair matrix: 8 min between ring-adjacent zones, 15 min between the two non-adjacent ones, 0 on the diagonal). Zone names here must exactly match `data/rides.json`'s `zone` values — nothing validates that at runtime beyond a `KeyError` if they drift, so keep them in sync by hand if either file is edited.

## Scripts

- `scripts/build_portaventura_dataset.py` — streams `data/raw/waiting_times.csv` in chunks, keeps only PortAventura World rides with the ride actually open, and writes `data/processed/portaventura_wait_times.parquet`. Run with `.venv\Scripts\python.exe scripts\build_portaventura_dataset.py`. Use this as the template for any similar chunked extraction (e.g. a Tivoli Gardens equivalent) rather than re-reading the raw CSV from scratch each time.
- `scripts/build_baseline_lookup.py` — reads `portaventura_wait_times.parquet` and writes `data/processed/baseline_wait_lookup.parquet`: median `WAIT_TIME_MAX` grouped by `ride, hour, day_of_week, month`. Intended as the baseline/reference table for later modeling work (e.g. an anomaly or uplift model would compare live wait against this).
- `scripts/train_wait_time_model.py` — trains a LightGBM model (native `lgb.train` API — scikit-learn is not installed, so don't use `lgb.LGBMRegressor`) on `ride, hour, day_of_week, month, attendance, temp, rain`, time-split train=2018-2021/test=2022 (never random-split this data — it's a forecasting problem). Attendance comes from `attendance.csv` filtered to `FACILITY_NAME == "PortAventura World"`; weather is daily-aggregated (mean temp, summed `rain_1h` with NaN treated as 0) from `weather_data.csv`, which covers a single fixed lat/lon ("Custom location", ~Paris coordinates — not actually PortAventura's location, but it's the only weather source available) rather than being per-park. Attendance only starts 2018-06-01, so rows before that have NaN attendance; left as NaN and handled natively by LightGBM's missing-value splitting rather than imputed. Saves the model to `models/wait_time_lgbm.txt`. Unlike `data/processed/`, `models/` is **committed** (not git-ignored) — `wait_time_lgbm.txt` is tracked so it deploys with the repo to Streamlit Cloud, which has no way to run this training script itself. Re-run this script and commit the result to update the deployed model; don't let a regenerated-but-uncommitted model silently drift from what's actually deployed.

**Important finding**: the pre-built baseline lookup as saved is not a fair comparison for the time-split model, because it was fit on all years 2018-2022 (including the test period) — it has already seen 2022's actual medians. `train_wait_time_model.py` therefore also recomputes a train-only version of the same lookup (fit on 2018-2021 only) for the fair comparison. Last run: model MAE 9.89 vs. fair (train-only) baseline MAE 11.49 — the model wins — vs. the leaky all-years baseline MAE 9.08, which beats the model only because of the leakage. Use the train-only number as the real baseline to beat.

One ride (Vertical Drop) only has 2 months of data and 1,623 rows total — likely opened/closed mid-period. Excluding it from monthly aggregates barely changes results, so ride-mix isn't a meaningful confound for the by-month seasonality numbers. Individual rides also don't have data on every calendar day in their date range (~75-80% coverage is typical) even though they report across the full range of operating hours (9am-10pm) — treat missing ride-days as no data, not as zero wait.

## LLM layer

- `src/tags.py` — the single source of truth for the ride-tag vocabulary: `ALLOWED_TAGS = ["water", "thrill", "family", "kids", "coaster", "spinning", "heights", "indoor"]`. Anything tagging rides or parsing tag-like constraints (e.g. `rides.json`'s `tags` field once populated) should import from here rather than hardcoding the list, so the vocabulary only ever changes in one place.
- `src/extract.py` — turns a natural-language planning request into validated constraints (`arrival_time`, `end_time`, `max_height_cm`, `exclude_tags`, `prefer_tags`, `is_planning_request`) by calling Claude Haiku (`claude-haiku-4-5-20251001`) with a forced tool call (`tool_choice={"type": "tool", ...}`) so the response is JSON matching a fixed schema, then re-validates it in a plain-dataclass `Constraints.from_dict` (format/type checks — there's no pydantic in this project). `exclude_tags`/`prefer_tags` are constrained to `tags.ALLOWED_TAGS` both in the tool's JSON schema (`enum`) and again defensively in `from_dict` (any tag outside the vocabulary — from a model that ignores the enum, or from hand-built input — is silently dropped, and duplicates are collapsed, rather than raising). `is_planning_request` (bool, default `True`, always present in the schema's `required`) is `True` only if the request resolves to at least one real field — a clock time or named convention, party/height details, or ride preferences — and `False` for general park questions ("what time does the park close?"), small talk, or gibberish, *even if* it mentions a schedule-related word without stating the visitor's own plan; a vague relative duration with nothing else concrete ("we only have 2 hours") is also `False`. Reads `ANTHROPIC_API_KEY` from `.env` via `python-dotenv`. Run `python src/extract.py` for 3 built-in test cases (no pytest installed — this is a plain runnable script, not a test suite), or `python src/extract.py "<request text>"` for ad hoc input. Since `src/extract.py` does `from tags import ALLOWED_TAGS` (not a relative/package import), always run scripts in `src/` directly (`python src/extract.py`), not as a `-m src.extract` module.

**Gotcha already hit once:** adding `is_planning_request` alone (without also adding the explicit "never use a placeholder" instruction below) made Haiku start returning the literal string `"<UNKNOWN>"` for `arrival_time`/`end_time` on ambiguous requests instead of omitting them, tripping `ConstraintValidationError` on every run of case 10 ("we only have 2 hours before we have to drive back"). The system prompt now explicitly says: *never fill an unknown field with a placeholder like `"<UNKNOWN>"`, `"N/A"`, or `""` — omit it, even when `is_planning_request=true`.* If you touch this prompt again and see `<UNKNOWN>`-shaped `ConstraintValidationError`s reappear, this is almost certainly why — don't just catch the exception in `evaluate.py`, fix the prompt.
- `src/evaluate.py` — runs every case in `data/eval_set.json` through `extract.py` then `planner.py` and reports four independent metrics: **extraction accuracy** (does every field named in a case's `expected` dict exactly match extraction output — list fields compared as sets, fields the case doesn't mention aren't checked) both overall and per-field; **plan constraint-satisfaction rate** (does the schedule built from the *extracted* constraints actually honor them — no ride over `max_height_cm`, none with an excluded tag, nothing outside `[arrival_time, end_time)` — this checks `planner.py`'s own correctness, independent of extraction accuracy); **prefer-tags satisfaction** (for the subset of cases whose *extracted* `prefer_tags` is non-empty, what fraction of the schedule's first `PREFER_TAGS_WINDOW=5` rides match at least one preferred tag — `None`/not counted for cases without `prefer_tags`, reported as a mean over the cases where it applies); and **zone-clustering comparison** (`build_schedule_greedy` vs the default `build_schedule`/`build_schedule_zoned`, mean total wait/walk/zone-changes/rides across all cases via `planner.schedule_stats` — see the `planner.py` entry above for the actual numbers and what they mean). Uses a fixed `EVAL_DATE = 2022-07-15` (not `date.today()`) so results are reproducible run to run in everything *except* the LLM call itself. `extract.py` sets `temperature=0` (passed via `extra_body`, since this SDK build's typed `messages.create` signature doesn't expose `temperature` directly — checked with `inspect.signature`), but that only *reduces*, not eliminates, run-to-run noise: 3 consecutive evaluate.py runs scored 76.0%/80.0%/80.0%, and even the two 80.0% runs differed in raw extracted output on an unchecked field (case 14's `arrival_time`: `None` vs `"09:00"`). Don't read a 1-2 case swing as a regression without re-running a few times first — or better, use `python src/evaluate.py --runs N`, which repeats the full eval N times and reports mean/min/max for both metrics plus which case IDs fail on every run ("consistently fail") vs. only some ("intermittently fail"); a case that's consistently failing is a real prompt gap worth fixing, one that's intermittent is likely just sampling noise. Catches `ConstraintValidationError` per-case (Haiku occasionally returns something extract.py's own validation rejects, e.g. a literal `"<UNKNOWN>"` for a time field) so one bad case doesn't abort the whole run — that case is scored as a failure instead. Run `python src/evaluate.py`. `data/eval_set.json` (25 hand-written cases plus a `_decisions` block spelling out the height/time conventions used to write `expected`, e.g. "until close" → `22:00`) is committed.

Extraction accuracy history (same 25 cases, tracks prompt changes in `extract.py`'s `SYSTEM_PROMPT`):
| | extraction accuracy | plan constraint-satisfaction | prefer-tags satisfaction |
|---|---|---|---|
| Before adding `_decisions` time/height conventions | 68.0% (17/25) | 96.0% (24/25) | not measured yet |
| After conventions (park-closes/morning/after-dinner/toddler/small-child + "reservation time is end_time, not arrival_time") | 76.0-80.0% (noisy, see below) | 100.0% (25/25) | not measured yet |
| After making prefer_tags a hard priority tier (see `planner.py` note below) | 76.0% (19/25) | 100.0% (25/25) | 86.7% (mean over the 12 cases with non-empty extracted `prefer_tags`) |
| After adding `is_planning_request` | 76.0% (19/25) | 100.0% (25/25) | 91.7% (mean over 12 cases) |

Remaining extraction failures are mostly `prefer_tags`/`exclude_tags` under-/over-inference on vague requests (e.g. "keep it gentle" → model adds `kids` beyond expected `family`; "most intense stuff" → model adds `coaster` beyond expected `thrill`) rather than a conventions gap — read `python src/evaluate.py`'s failure table for the current specifics before trying to fix more of these, since exact numbers drift between runs.

`is_planning_request` didn't move the aggregate score outside its established 76-80% noise band, but it did change *which* cases fail: case 8 ("most intense stuff you've got") started passing, while a new failure appeared — case 7 ("it's pouring rain today, what's worth doing?") now comes back `is_planning_request=False` with empty `prefer_tags`, where it previously extracted `prefer_tags: ['indoor']`. The model is treating that question-shaped-but-preference-implying request as out of scope. Worth knowing if you tune `is_planning_request`'s prompt wording further — it's a real, if narrow, side effect, not just noise.
- `src/planner.py` — same-day scheduler. Two implementations share all the low-level machinery (`_cheapest_in`, `_preferred_pool`, `_predict_wait` via `models/wait_time_lgbm.txt`, `filter_rides` for height/`exclude_tags`, prefer_tags as a **hard priority tier, not a tiebreaker** — as long as a preferred ride is reachable before `end_time`, it's chosen over a cheaper non-preferred one):
  - `build_schedule_zoned` (the default, exposed as `build_schedule`) — works through **one zone at a time**: cheapest-predicted-wait first within the current zone (prefer_tags still hard-priority, but scoped to that zone — a zone's *non-preferred* rides still get done before leaving it, since "exhausted" means the whole zone, not just its preferred subset), and only moves zones once the current one has nothing left reachable. When moving, an adjacent zone (`data/zones.json`) is tried before a distant one — if multiple adjacent zones still have candidates, prefer_tags and cheapest-wait apply across their combined pool. Every zone is tried as the *starting* zone; whichever full schedule has the lowest total `(wait + walk)` time cost is kept (ties broken by more rides completed).
  - `build_schedule_greedy` — the original park-wide approach: at every step, picks the single cheapest-wait reachable ride anywhere in the park, using a flat `WALK_DIFF_ZONE_MIN=10` for any zone change. Kept *only* for comparison against the zoned version (`compare_greedy_vs_zoned`) — this is the one prone to criss-crossing zones.
  - `data/zones.json` (committed, fabricated like the rest of the zone layout) replaces that flat 10-minute inter-zone penalty for the zoned scheduler with a real per-pair walk-time matrix: the 5 zones are arranged as a ring (Mystic Quarter–Kids Kingdom–Lagoon Cove–Coaster Canyon–Thrill Peak–back to Mystic Quarter), ring-adjacent pairs are 8 minutes, the two non-adjacent pairs from any zone are 15 minutes. `WALK_SAME_ZONE_MIN=5` (intra-zone) is unchanged and used by both schedulers.
  - `schedule_stats(schedule)` reconstructs total wait/walk minutes and zone-change count from a built schedule's `time`/`predicted_wait_min`/`zone` fields alone (exactly, not approximated — it mirrors the same rounding the schedulers use to advance the clock), so it works on either scheduler's output without the schedule format needing to carry extra bookkeeping. `compare_greedy_vs_zoned(constraints, ...)` builds both schedules for the same constraints and returns their stats side by side; `print_comparison(...)` renders it as a table. Run `python src/planner.py` for a built-in example plus this comparison.
  - **Measured trade-off** (mean over all 25 `data/eval_set.json` cases, via `evaluate.py` — see below): zoned cuts walk time ~34% (139.8→92.2 min) and zone changes ~74% (11.6→3.0) for essentially the same rides completed (17.4→17.5), but at a slightly *higher* mean wait (279.4→287.4 min, +2.9%) — clustering within a zone sometimes means riding something with a marginally longer queue instead of chasing a cheaper one across the park. This is a genuine trade-off, not a strict win on every axis; report all three numbers together, not just the flattering ones.
  - Requires `models/wait_time_lgbm.txt` to already exist. It's committed (see `scripts/train_wait_time_model.py` above), so it's already there after a normal clone; re-run the training script and commit the result if you need to refresh it. Since there's no real future attendance/weather to predict on, unset `attendance`/`temp`/`rain` default to that target date's historical monthly average (`_monthly_defaults()`, computed from `attendance.csv`/`weather_data.csv`); pass a `date` to control which month/day-of-week is used, since `Constraints` itself carries no date. The model's `ride` categorical codes were fixed at training time to the sorted order of the *full* 26-ride list — `_predict_wait` always builds that categorical against all of `data/rides.json`, never just the filtered candidates, or predictions would silently be wrong.

## UI

- `app.py` (project root, not `src/`) — Streamlit front-end: a text box + button run `extract_constraints` then `build_schedule`, showing the extracted constraints in a `st.expander` and the resulting schedule as a table (`st.dataframe`) with a total-predicted-queue-minutes metric. Run with `.venv\Scripts\python.exe -m streamlit run app.py`. Since it lives at the project root while `extract.py`/`planner.py` use plain sibling imports that only resolve with `src/` itself on `sys.path`, `app.py` inserts `src/` into `sys.path` before importing them — don't "fix" this into a `from src.extract import ...` absolute import, since `extract.py`'s own internal `from tags import ALLOWED_TAGS` would then fail. `load_model()`/`load_rides()` are wrapped in `st.cache_resource`/`st.cache_data` respectively so the model and ride list load once per session, not on every click. A missing `models/wait_time_lgbm.txt` raises `lightgbm.basic.LightGBMError`, *not* `FileNotFoundError` (verified directly — worth remembering if you touch this error handling, since catching the wrong type silently lets the real error propagate as an unhandled Streamlit exception instead of the friendly message).

**Visual design**: a fixed, cover-sized, dark-overlaid background photo (`assets/background.jpg`, a lit swing ride against dusk clouds) sits behind everything, with content in two "glass" panels (`st.container(key="hero_panel")` for the title/input, `st.container(key="results_panel")` wrapping *everything* from the empty-input warning through the schedule table — nothing meaningful is left floating directly on the photo). CSS is injected once via `st.markdown(..., unsafe_allow_html=True)`, targeting Streamlit's documented `st-key-<key>` class convention (confirmed in this venv's own `streamlit/.agents/skills/developing-with-streamlit/references/theme.md`, which otherwise says *not* to use custom CSS for theming unless explicitly asked — this app is the explicit-ask exception). All panel/text colors are hardcoded hex/rgba, not Streamlit theme CSS variables, so the look is identical regardless of the user's light/dark theme setting. `get_background_b64()` reads and base64-encodes the image once (`@st.cache_data`) rather than on every rerun, since Streamlit can't serve an arbitrary local file path directly.

**Gotcha already hit once (input styling)**: overriding just `.st-key-hero_panel input`'s `color`/`background` was not enough to make typed text visible — the actual visible box is a separate parent (`[data-testid="stTextInputRootElement"]`) with its own opaque background from Streamlit's default theme, which showed through behind the input's own near-transparent background, making near-white text invisible against it (confirmed via a headless-Chrome CDP screenshot with real typed text, and via `getComputedStyle`). Fixed by setting the background on `stTextInputRootElement` instead and making the `<input>` itself `background: transparent`. If you re-theme this input, style the root element, not just the `<input>`.

**Gotcha already hit twice (background scoping)**: the background+overlay is painted on a dedicated `<div class="app-bg">` with `position: fixed; inset: 0; z-index: -1` (with `.stApp { background: transparent }`), *not* as `.stApp`'s own `background-image`. Painting it directly on `.stApp` risked the image/gradient being sized or positioned against `.stApp`'s own (possibly page-tall) box rather than strictly the viewport, depending on Streamlit's actual DOM/scroll structure — a `position: fixed` div sidesteps that ambiguity entirely and is guaranteed viewport-pinned. Note this still means the gradient is viewport-relative, not document-scroll-relative: "darkest toward the bottom" darkens the bottom of whatever's currently in view, not the bottom of the full scrollable page — the real fix for "the table is unreadable over the photo" is `results_panel`'s own near-opaque background (`rgba(6, 9, 15, 0.9)`, darker/more opaque than `hero_panel`'s `rgba(10, 15, 24, 0.68)`), which dominates over whatever the gradient happens to be doing underneath it at that scroll position.

**Verified visually** (headless Chrome via CDP — `Runtime.evaluate`/`Input.dispatchMouseEvent`/`Input.insertText`/`Page.captureScreenshot`, since the interactive Chrome extension wasn't available this session): full flow with real typed input at desktop width, at a 390px-wide viewport (no horizontal overflow, panels reflow with reduced padding), and the out-of-scope fallback path (`st.info` + "Default full-day plan" heading) all render correctly. Also verified the actual scrollable element is `[data-testid="stMain"]` (not `window`/`document`, and not `.stApp`) — scroll that one if you need to screenshot/test a scrolled state programmatically. A screenshot taken at an artificially tall viewport (e.g. 1400x2200, taller than any real browser window) is misleading here: `background-size: cover` on the portrait (3018x4008) source photo will stretch to reveal nearly its full vertical extent — including a much brighter lower section — in one unscrolled paint; that's a test artifact, not a real-scroll bug. Test at a realistic viewport (e.g. 1400x900) and actually scroll `stMain` instead.

**Process gotcha hit once**: a long-running `streamlit run app.py` process (started directly by the user, outside this session) held a stale cached `extract` module in memory from before `Constraints.is_planning_request` existed, causing a real `AttributeError`-shaped crash even though the on-disk file was already correct — Python doesn't re-import an already-loaded module just because its file changed, and Streamlit's local-file watcher doesn't always catch this reliably for modules reached via a runtime `sys.path` insert (as `app.py` does for `src/`). If a "no such attribute" crash doesn't reproduce against the current file, suspect a stale running process before suspecting the code — check `netstat`/`Get-Process` for an old `streamlit`/`python` process and restart it.

**Out-of-scope handling**: when `not constraints.is_planning_request`, or when every constraint field is at its empty default (`_no_meaningful_constraints()` — belt-and-suspenders in case the model mis-flags `is_planning_request` itself), the app shows an `st.info` with 3 example request phrasings and labels the schedule below "Default full-day plan" instead of "Your schedule" — it still builds and shows a real schedule (using the default 09:00-22:00, unfiltered constraints), just relabeled, rather than blocking the user. The text input also has inline placeholder text and a hint caption underneath showing a good request shape.
